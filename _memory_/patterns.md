# Patterns et conventions (mis à jour le 2026-08-31, 13 h 30)

**Nommage.** Vérifications `FAMILLE-NN` (ROBOTS, SNIP, IDX, SD, TAG, FRESH, REND, PERF, AI, STRAT, LVL1) ; lignes de la checklist `CL-NN` (01 à 15). Sévérités : Critique, Important, Mineur, Info. Verbes : audit, strategy, build, checklist (jamais « launch » : la skill ne déploie rien, D23), console. Entrées de référence `ACC-NN` pour `acces.md`. Dossiers : `seo/audits/<AAAA-MM-JJ>-n<niveau>[-k]/`, `seo/strategy/<AAAA-MM-JJ>[-k]/`, réservés atomiquement (`mkdir` non récursif, suffixe au premier libre, jamais écrasés).

**Markdown strict + parseur + lint.** Tout fichier lu par un script a un format fixe et un parseur dédié : `strategy.md` (`parseStrategy`, `lint-strategy.ts`), `report.md` (`parseReport`, `lint-report.ts`), `checks/*.md` (`parseChecks`), recettes `### Titre (ID, ID)` avec `Fichiers`, `Recette`, `Piège`, `Source` (`parseRecipes`, les blocs de code ignorés ; `consoles.md` et `acces.md` réutilisent ce format avec `Chemin` à la place de `Fichiers`, ligne ignorée par le parseur et vérifiée par regex), `seo/checklist.md` (`parseChecklist` : une ligne `- [ ] <libellé> · <auto|main|action> · <note>`, sous-lignes `  - …`, en-tête `Mise en ligne : … · Dernier passage : … · Audit local : … · Audit prod : …`, ligne inconnue = erreur, rien réécrit).

**Fetch injecté.** Tout module qui parle au réseau reçoit son `fetch` en paramètre (`Fetcher` dans `actions.ts`, `ChainFetcher` dans `ancien-sitemap.ts`, `fetcher` dans `keywords.ts`) ; le CLI passe le vrai, les tests un faux qui journalise les appels et asserte sur le corps envoyé, jamais sur un mock. Une écriture sortante est toujours derrière un drapeau explicite (`--agir`) et un OK de Romain dans la skill.

**D5, sources.** Une vérification ou une recette sans `Source` officielle citée mot pour mot ne se livre pas ; `check-sources.ts` retrouve chaque citation sur sa page. Domaines : `OFFICIAL_DOMAINS` (moteurs) pour les rapports et les checks, `BUILD_DOMAINS` (+ nextjs.org, vercel.com, react.dev) pour les recettes.

**Décisions notables.** D9 couche stratégique dès que `strategy.md` existe ; D11 jamais un chiffre Google, Bing vide = « non mesurable gratuitement » daté ; D15 tout le réseau dans `collect.ts` ; D16 textes visibles (h1, première phrase) via une table validée par Romain avant modification, puis remplacés (l'ancien texte disparaît) ; D17 build lance serveur local + audit niveau 2, 2 passages max ; D19 genre par id (code / texte / hors-build) dans une table testée ; D21 base canonique = hôte observé au niveau 0. Depuis le 29/08 : un plan parti d'un audit local rapatrie les hors build ouverts du dernier audit n0, champ `origine` (R-6, option a choisie par Romain).

**Erreurs.** Les CLI impriment `erreur : …` et sortent 1, usage 2, jamais une stack ; `StrategyError` et `ReportError` portent `errors[]`. Un chemin explicite absent (`--strategy-path x.md`) est une erreur consignée ; le défaut absent est silencieux. Une donnée secondaire illisible (rapport n0 pour la fusion des hors build) est un `attention : …` sur stderr, jamais un silence : la skill répète ces lignes à l'utilisateur.

**Tests (`bun test`, 375 au 29/08 soir).** Fixtures réelles (fichiers de chico, réponses Bing et Wikimedia), jamais un jouet quand un vrai échantillon existe. Invariants sur le catalogue (« tout id a un genre »), jamais un compte figé. CLI testés par `Bun.spawnSync` sur un site factice en `mkdtemp` (`fakeSite()` dans `plan-cli.test.ts`) ; `Bun.spawn` asynchrone quand le sous-processus appelle un `Bun.serve` du même process (sinon interblocage). Interdit : lire le code source depuis un test, asserter sur un mock, un `.catch()` sans assertion de rejet préalable (il passe à vide si la promesse résout).

**La mutation est le vrai gate d'une revue (chantier 5, 29/08).** Un test vert ne prouve rien tant qu'on ne l'a pas vu échouer. Sur ce chantier, quatre défauts majeurs ont été trouvés uniquement par mutation, jamais par lecture : deux tests anti-fuite qui ne pouvaient pas échouer, un test d'AC qui n'exerçait pas son AC (retirer la garde laissait 15/15 verts), et un filet anti-tiret cadratin qui ne voyait que les branches déjà couvertes. Pratique adoptée : tout garde-fou (anti-fuite, anti-écriture, invariant de fichier) se prouve en mutant le code, constatant l'échec, remettant en état, et en collant le message d'échec dans le rapport. Automatisable : boucler sur les littéraux d'un module, injecter un caractère, relancer la suite, compter les survivants. **Attention à l'outil lui-même** : une regex sur guillemets droits ne voit pas les chaînes dans les gabarits à accents graves, angle mort réel rattrapé par un relecteur.

**Aucun champ inventé sans échantillon observé.** Quand une API n'a pas pu être capturée, le décodage s'arrête à l'enveloppe et rend la charge telle quelle, sans supposer un champ ; le jour où la capture existe, on nomme les champs et on met en forme. Appliqué aux quatre méthodes Bing du chantier 5, restées brutes le matin (compte vide) et mises en forme le soir (compte rempli par Romain).

**Le plan est réaligné sur le code livré après chaque revue.** Quand un correctif change le code, les blocs correspondants du plan sont remplacés par le contenu exact des fichiers du dépôt, vérifié ligne à ligne. Sans ça, une reprise du plan réintroduit les défauts que la revue vient de trouver.

**Textes tiers.** Aucun em dash dans `plugin/**` (rapports, références, gabarits, SKILL.md, README) : lint et tests le refusent. Le filet ne vaut que par sa couverture : toute chaîne littérale d'un module de rendu doit apparaître dans au moins une sortie du tableau contrôlé, sinon un em dash y passe sans être vu (vérifié par mutation, 29/08). Français, citations en anglais entre « ».

**Git.** Commits en français, préfixes `feat(build):`, `fix(audit):`, `test(…):`, `docs:`, `seo-build(plan):` ; trailer Co-Authored-By ; fusions `--no-ff` avec message. **Le dépôt a un remote depuis le 31/08** (`git@github.com:eRom/erom-agence-seo.git`) : `main` y est poussé sur décision de Romain, jamais d'office. `build` commite dans le repo du site : `seo(ID, ID): …`, branche `seo-build-<date>` si on part de main ; Romain fusionne et pousse le site lui-même.

**Recette vivante.** Un document par chantier (`docs/superpowers/plans/<date>-erom-seo-chantier-N-recette.md`) : procédure exacte par AC, puis une section « Résultats du <date> » avec OK / KO et les sorties réelles, chaque écart numéroté `R-n` avec sévérité et cause, un bilan (OK, KO, à trancher, mineurs), puis une section « Correctifs du <date> » quand Romain a tranché. Les AC observables après coup (commits, rapport, ports, diff) se vérifient depuis les fichiers et le transcript jsonl du cobaye ; ceux qui demandent un œil humain (liste des textes, message final) se lisent dans le transcript.

**Process de chantier.** Fable : brainstorming (2 options, une question par message), spec avec `Battu :` par décision et `## Critères d'acceptation` (AC-n, Comportement, Vérifié par), plan avec tout le code, code pur exécuté dans le scratchpad avant écriture. Sonnet : exécution subagent-driven dans un worktree frère `erom-agence-seo-<sujet>`, un commit par tâche, rapport dans le scratchpad. Variante du 29/08 : brief `SendMessage` à la session paire du cobaye (elle a la table validée dans son contexte), AC avec sorties réelles exigées, retour par `SendMessage`. Fable : relecture du diff complet, tests et sources relancés, retouches mineures directes (une erreur avalée, une spec désalignée), fusion, recette, note de reprise. Variante du chantier 4 (29/08) : Fable orchestre en subagent-driven dans la même session, implémenteurs et reviewers Sonnet (un par tâche, brief extrait du plan par awk sur « Tâche N », rapport dans `.superpowers/sdd/<plan>/`), relecture adversariale du plan avant la tâche 1, revue finale de la branche sur Fable, une seule vague de correctifs puis une re-revue ciblée ; registre `progress.md` avec chaque `Ruling:` et son coût si faux, liste exhaustive rendue à Romain à la fin. Recherche pré-plan : trois briefs `search-builtin` en parallèle, conventions externes recurlées par la session mère et collées dans `docs/recherches/`.

**Ce que le chantier 5 a ajouté au process (29/08, Opus orchestrateur).** La revue adversariale du plan **avant** la tâche 1 a rendu 2 critiques, 9 importants et 10 mineurs, tous réels : elle extrait les blocs de code du plan, les exécute dans une copie du dépôt, et lance les contrôles réseau (`check-sources.ts`) pour de vrai. Un défaut trouvé là coûte un correctif de plan ; trouvé pendant l'exécution, il coûte un cycle revue-correctif-re-revue par tâche qui en hérite. Les briefs se **régénèrent** depuis le plan avant chaque dispatch, jamais d'avance : un brief généré avant un correctif du plan envoie l'implémenteur sur une consigne périmée. La session mère revérifie chaque livrable de ses propres mains (suite, `git status`, `git diff --stat`, mutation ciblée) avant de dispatcher la revue, et le registre `progress.md` est copié dans `docs/superpowers/journaux/` avant la suppression du worktree, sinon les arbitrages meurent avec lui.

## Patterns du niveau 1 (30/08)

- **Une panne se dit par un champ, jamais par une absence.** Les blocs de résultat ne sont pas optionnels : `google` et `bing` existent toujours, et portent `error`. Deux façons d'exprimer « pas de données » en est une de trop.
- **Chaque panne partielle a son propre champ.** `error` (le bloc entier), `sitemapsError` (les sitemaps seuls), `searchError` (l'appel de requêtes seul). Sans ça, une panne partielle laisse des données vides que le rapport lit comme un constat : « aucune impression » au lieu de « Google n'a pas répondu ». Chaque texte du catalogue **garde son ou ses champs d'erreur avant de lire ses données**.
- **Un compte de pages a trois catégories, pas deux** : réussies, jugées négativement, et **non jugées** (l'appel a échoué). Invariant testé : `total === indexed + notIndexed.length + notInspected.length`. Sans la troisième, une page dont l'API n'a pas répondu est accusée.
- **Couture d'injection pour rendre une garantie observable.** `CollectOptions.consoleFetcher` et `consoleAuth` sont absents en usage réel et fournis par les tests : c'est ce qui permet de prouver qu'aucune requête ne part sans le drapeau, et d'éviter qu'une suite de tests lance `gcloud`.
- **Le module de collecte est pur, l'appelant écrit.** `level1.ts` rend la liste des fichiers à poser ; `collect.ts` seul touche au réseau et au disque. C'est ce qui rend testable « aucune requête ne part ».
- **Revue par mutation.** La méthode qui a trouvé tous les défauts sérieux de ce chantier : écrire l'implémentation fausse, lancer la suite, et regarder si un test casse. Un test qui reste vert devant un code qui ment est le défaut le plus coûteux, parce qu'il donne confiance à tort. À appliquer aussi aux textes du catalogue, en se demandant ce qu'ils feraient écrire de faux.


## Patterns du chantier 6, le rapport client (31/08)

**CLI à deux gestes autour du jugement du modèle.** Quand le modèle doit écrire au milieu d'un flux, le CLI se coupe en deux : un geste qui sort la matière sans rien écrire (`--preparer`), le modèle rédige, un geste qui valide puis écrit (`--rendre`). La garantie centrale est qu'un lint qui refuse **n'écrit rien** : on ne produit jamais un artefact dont l'entrée a été rejetée. Testé en vérifiant l'absence du fichier de sortie après un refus, pas seulement le code de retour.

**Défense en profondeur sur ce qui sort de l'agence.** Le lint refuse à l'écriture, le rendu retire en dernier recours. Les deux, jamais l'un seul : le rendu est la dernière porte avant le tiers, et il doit tenir même si le lint est contourné. Corollaire appris à ses dépens : un rendu qui **retire** du contenu doit avoir un lint qui le **refuse** en amont, sinon il ampute du texte légitime en silence.

**Une garantie formulée sur un format ne protège pas d'un autre format.** Trois fuites d'identifiants vers le client sur ce chantier, par trois portes : l'indentation d'un commentaire, son emplacement hors bloc, puis un commentaire **CSS** que deux campagnes de chasse ont manqué parce qu'elles surveillaient le Markdown et le HTML. La question à poser n'est pas « ce format est-il filtré » mais « quels chemins atteignent la sortie ».

**Deux fonctions qui décident du même motif doivent le tester à l'identique.** `blocs()` matchait sur la ligne brute, `idsVisibles()` sur la ligne trimmée : un commentaire indenté échappait au parseur tout en restant exempté du détecteur. Quand deux fonctions se répartissent la garde d'un même motif, leur solidarité se verrouille par un test qui casse **dans les deux sens** (vérifié par mutation des deux côtés).

**Un lint mécanise ce qui est mécanisable, et la limite s'écrit.** La couverture d'une trouvaille est un pointage d'identifiant : aucun lint ne peut vérifier qu'un paragraphe français parle bien de ce qu'il déclare traiter. Plutôt qu'une heuristique (longueur minimale, plafond d'identifiants) qui ferait des refus arbitraires, la limite est nommée dans la spec et la relecture du modèle gagne un défaut dédié, placé **en tête** de sa liste.

**Quand une décision amende une règle, la propager là où la règle est énoncée.** D49 a été écrite dans la spec et appliquée dans le lint, mais le `SKILL.md` a gardé la formulation d'avant pendant tout le chantier, et le CLI n'affichait pas la matière du cas concerné. Une règle vit à trois endroits : la spec qui la décide, le code qui l'applique, le mode d'emploi que le modèle lit.

**Un compte de tests annoncé dans un plan est un piège.** Annoncé faux (8 au lieu de 11, 464 au lieu de 467), il fait lire une suite saine comme un échec. Formuler le critère en « zéro échec, aucun test sauté » et donner le compte à titre indicatif.
